# chr-container-rose

Образы RouterOS CHR (x86_64, raw) с установленными пакетами `container` и
`rose-storage` и настроенным `device-mode`. Сборка и публикация — GitHub
Actions.

## Состав образа

- стоковый образ CHR указанной версии и официальные пакеты `container` и
  `rose-storage` той же версии;
- `device-mode`: `mode=advanced`, `container=yes`, `traffic-gen=yes`;
- конфигурация сброшена `/system reset-configuration no-defaults=yes
  skip-backup=yes` без подключённых сетевых интерфейсов: первый интерфейс
  машины, на которую записан образ, получает имя `ether1`;
- лицензия `free`, пользователь `admin` с паролем по умолчанию, пустые
  scheduler'ы и system script'ы, в `rw/disk` только `skins`, в `rw/store`
  стоковый `autorun.scr`.

При пустой конфигурации RouterOS CHR создаёт DHCP-клиент на `ether1` при
загрузке.

## Релизы

[Releases](../../releases), каждый образ с файлом `.sha256`:

| Ассет | Загрузка |
| --- | --- |
| `chr-<версия>-container-rose.img` | BIOS; разметка стокового CHR |
| `chr-<версия>-container-rose-uefi.img` | UEFI; в BIOS не загружается |

UEFI-образ отличается от BIOS-образа только разделом 1 и таблицей разделов.
Раздел 1 (`EFI/BOOT/BOOTX64.EFI`) переформатирован из ext2 в FAT16 с теми же
файлами: UEFI-прошивка читает только FAT. Таблица — GPT с гибридным MBR,
раздел 1 типа `EF00`; схема та же, что вариант «jaclaz» в
[tikoci/fat-chr](https://github.com/tikoci/fat-chr). Раздел 2 совпадает с
BIOS-образом побайтно. Загрузочный сектор раздела 1 при форматировании
заменяется, поэтому BIOS-загрузка UEFI-образа не работает.

Описание релиза содержит SHA-256 и размер обоих образов, ссылку на запуск
workflow и коммит, из которого собраны образы.

## Процесс сборки

Команды в гостевую систему передаются скриптами, записанными в раздел `rw`
образа; последовательная консоль CHR для ввода не используется.

1. В стоковый образ записываются `rw/autorun.scr` и
   `rw/disk/build-stage2.rsc`. При первой загрузке `autorun.scr` ожидает
   адрес от встроенного DHCP-клиента, загружает оба пакета с HTTP-сервера
   сборщика, создаёт scheduler для второго этапа и перезагружает RouterOS;
   пакеты устанавливаются при загрузке.
2. Второй этап проверяет наличие пакетов, создаёт scheduler сброса
   конфигурации и выполняет `/system/device-mode/update container=yes
   traffic-gen=yes`. Сборщик отключает питание ВМ, что подтверждает
   изменение `device-mode`.
3. ВМ загружается без сетевого интерфейса; scheduler выполняет сброс
   конфигурации и перезагрузку. QEMU запускается с `-no-reboot`, перезагрузка
   гостя фиксируется по завершению процесса.
4. После загрузки без перезапуска ВМ выключается через ACPI без входа в
   систему; `rw/store/autorun.scr` заменяется стоковым.
5. Копия образа загружается с сетевым интерфейсом и проверочным скриптом,
   который выгружает состояние RouterOS в файлы. Сборщик проверяет пакеты,
   `device-mode`, имя `ether1`, лицензию, пользователей, отсутствие
   scheduler'ов и содержимое раздела `rw`; при расхождении сборка
   завершается ошибкой. Выгрузки сохраняются в артефакте запуска.
6. Из образа создаётся UEFI-копия (`img.sh uefi`: `mkfs.vfat`, `gdisk`).
   Сборщик сравнивает раздел 2 с BIOS-образом и загружает временную копию в
   QEMU с OVMF до приглашения `Login:`; при расхождении или отсутствии
   приглашения сборка завершается ошибкой.

Гостевые скрипты сообщают о ходе выполнения HTTP-запросами к сборщику. Код —
в [`builder/`](builder/).

## Каналы и расписание

| Канал | Релиз |
| --- | --- |
| stable | помечается как Latest |
| long-term | название с `(long-term)`, без пометки Latest |

Workflow **Build and Publish** запускается ежедневно в 04:00 UTC. Версии
каналов читаются из `https://upgrade.mikrotik.com/routeros/NEWESTa7.stable`
и `NEWESTa7.long-term`. Для версии без релиза выполняются сборка, проверка и
публикация. Каналы собираются в отдельных заданиях матрицы и не зависят друг
от друга.

Параметры ручного запуска:

| Параметр | Значения | Описание |
| --- | --- | --- |
| `channel` | `both`, `stable`, `long-term` | проверяемые каналы |
| `force` | `true`, `false` | пересборка версий с существующим релизом |
| `publish` | `true`, `false` | `false` — образ сохраняется как артефакт запуска, релиз не создаётся |
| `accel` | `kvm`, `tcg` | ускорение QEMU |

Без `force` существующие релизы не изменяются. С `force` предыдущий релиз и
его тег удаляются после успешной проверки новой сборки, непосредственно перед
публикацией. SHA-256 пересобранного образа отличается от предыдущего: образ
содержит временные метки и идентификаторы, созданные RouterOS при загрузке.

Тег релиза указывает на последний коммит, не изменяющий `.github/workflows/`:
`GITHUB_TOKEN` не создаёт теги на коммитах с изменениями workflow.

## Локальная сборка

```
python builder/build.py 7.24.4
```

Результат — в `<CHR_BUILD_ROOT>/out/`.

- **Linux:** `qemu-system-x86`, `ovmf`, `unzip`, `sfdisk`, `gdisk`,
  `dosfstools`, `sudo` для loop-mount; KVM
  при доступном `/dev/kvm`. `CHR_BUILD_ROOT` по умолчанию — `work/` в корне
  репозитория.
- **Windows:** QEMU (путь в переменной `QEMU`), 7-Zip, Docker Desktop для
  loop-mount. QEMU работает в режиме TCG. `CHR_BUILD_ROOT` по умолчанию —
  `D:\chr-build`.

## Исходные компоненты

RouterOS — продукт MikroTik; проект с MikroTik не связан. Стоковый образ и
пакеты загружаются с `download.mikrotik.com` и не модифицируются; изменения
вносятся средствами RouterOS: установка пакетов, `device-mode`, сброс
конфигурации. Для UEFI-образа дополнительно меняются файловая система
раздела 1 и таблица разделов.
